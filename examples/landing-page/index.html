How it works

It teases a spec out of the conversation, then holds itself to it.

From the moment it sees you're building something, your agent steps back and asks what you're really trying to do. Once it has a spec, it shows it to you in chunks short enough to actually read.

After you sign off on the design, it writes an implementation plan clear enough for an enthusiastic junior engineer with poor taste, no judgement, no project context, and an aversion to testing to follow. Then you say "go", and subagents work through the tasks one at a time, with a review after each.

It's not uncommon for an agent to work autonomously for a couple of hours without deviating from the plan you put together.

The basic workflow

Seven skills, in the order they fire.

  1. 01

    brainstorming

    Activates before writing code. Refines rough ideas through questions, explores alternatives, presents the design in sections for validation, saves a design document.

  2. 02

    using-git-worktrees

    Activates after design approval. Creates an isolated workspace on a new branch, runs project setup, verifies a clean test baseline.

  3. 03

    writing-plans

    Breaks the work into bite-sized tasks of two to five minutes. Every task carries exact file paths, complete code, and verification steps.

  4. 04

    subagent-driven-development or executing-plans

    Either a fresh subagent per task with a review after each — the most thorough — or every task inline in the current session with one review of the whole branch at the end, which is the cheapest.

  5. 05

    test-driven-development

    Enforces the cycle during implementation: write a failing test, watch it fail, write minimal code, watch it pass, commit. Code written before its test gets deleted.

  6. 06

    requesting-code-review

    Runs between tasks. Reviews the work against the plan and reports issues by severity. Critical issues block progress.

  7. 07

    finishing-a-development-branch

    Verifies tests, presents the options — merge, PR, keep, discard — and cleans up the worktree.

The agent checks for relevant skills before any task. These are mandatory workflows, not suggestions.

Step 05, in detail

Red, green, refactor — with the receipts.

Red · watch it fail → Green · minimal code → Refactor · then commit

A test that has never failed proves nothing, so the agent runs it and reads the failure before writing the implementation. The rule has teeth: implementation written ahead of its test is deleted, not retrofitted with a test afterwards.

The same stance runs through the rest of the library — evidence over claims, verified before anything is declared done.

When it misbehaves

Ask it what went wrong.

Sometimes a skill fires when it shouldn't, stays silent when it should, or the agent ignores its plan, repeats work, or burns more tokens than you expected. Say this:

› figure out what went wrong with superpowers in this session

diagnosing-superpowers reads the session transcript, reports what happened with line-level evidence, and — if you want it to — packages a scrubbed bundle for a bug report. Name a session id to examine an earlier one.

Install

Pick your harness.

Installation differs by harness, and each one installs separately. If you use more than one, run it in each.

/plugin install superpowers@claude-plugins-official

From the official Claude plugin marketplace. The Superpowers marketplace is the other route: /plugin marketplace add obra/superpowers-marketplace, then install superpowers@superpowers-marketplace.

$gemini extensions install https://github.com/obra/superpowers

Update later with gemini extensions update superpowers.

/add-plugin superpowers

In Cursor Agent chat — or search for "superpowers" in the plugin marketplace.

$devin plugins install obra/superpowers

Update with devin plugins update superpowers.

$agy plugin install https://github.com/obra/superpowers

Antigravity runs the session-start hook, so Superpowers is active from the first message. Reinstall with the same command to update.
